# Merkle Data Engineer Case Study — Open Questions

## 1. What steps are missing to industrialize the solution?

The notebook is a reproducible batch prototype: it reads two CSV files, overwrites raw and cleaned Delta tables, and publishes `top_item` after validation. Production would need the following additions, sized to this pipeline:

- **Orchestration and scheduling:** run ingestion, cleaning, validation, and mart publication as ordered Databricks job tasks. Schedule according to source arrival and prevent overlapping runs from overwriting the same tables.
- **Incremental and idempotent processing:** first establish whether files are complete snapshots or incremental deliveries. Full replacement remains reasonable for these small snapshots. For recurring incremental files, track processed file versions and merge complete logical events by `event_id` after validating their parameters. Raw ingestion must preserve all parameter rows. Late or corrected views require recalculating affected item/year counts and platforms, then ranks for every item in each affected year.
- **Schema contracts and evolution:** agree required CSV columns, payload fields, parameter names, identifier formats, and timestamp timezone with the source owner. Keep Layer 1 attributes STRING; review schema changes explicitly rather than silently dropping new parameters.
- **Data-quality tests:** retain the current key, event-consistency, parameter-conflict, referential-integrity, and reconciliation checks. Add checks that populated raw values survive numeric and timestamp conversion, and enforce the required-parameter diagnostics currently printed by the notebook. Failed validation must block downstream publication.
- **Monitoring, logging, and alerting:** record input file versions, row counts, invalid-record counts, durations, and yearly reconciliation results for each run. Alert on failures, missing expected deliveries, and unexpected changes in view volume; static historical files do not require artificial freshness alerts.
- **Retries and backfills:** retry transient S3 or compute failures, but investigate data-contract failures. Support explicit file/date-range reruns and recompute affected years so late data cannot leave stale ranks. Publish only after successful checks; retain the last successful mart for consumers.
- **CI/CD and environments:** version code and dependencies, validate changes in separate development/test schemas, and deploy through an existing CI pipeline. Include repeat-run, late-arrival, and platform/ranking tie cases alongside a representative dataset.
- **Secrets and IAM:** use a service identity with least-privilege S3, catalog, and compute access. Keep credentials in managed secrets or supported identity-based authentication, never in the notebook or repository.
- **Lineage and documentation:** record source-to-table dependencies, event grain, field meanings, ownership, and recovery steps. Preserve the documented `RANK()` semantics and alphabetical platform tie rule.
- **Performance and cost:** use appropriately sized, auto-terminating compute and monitor scan volume and file sizes. Keep year partitioning for the event table and the small mart unpartitioned. Introduce incremental processing or file maintenance only when data growth justifies it.

## 2. If dbt-core were used, how would the architecture change and what additional cloud resources would be needed?

**dbt-core is a transformation tool, not an ingestion tool or scheduler.** S3 CSV ingestion and creation of the all-STRING Layer 1 Delta tables would remain a Databricks/PySpark task outside dbt.

With `dbt-databricks`, most transformation logic in Layer 2 and Layer 3 could become dbt SQL models: item casting and renaming, event payload extraction and parameter pivoting, and the `top_item` aggregates and window functions. Raw Delta tables would be declared as dbt sources, with model dependencies expressed through `source()` and `ref()`. The three-layer design, grains, types, partitioning, and tie semantics would remain unchanged.

CSV quoting/escaping, file tracking, and ingestion error handling should stay outside dbt. If JSON parsing and pre-pivot conflict validation are clearer in PySpark, retain them as a small upstream task reading Layer 1 and expose its output to dbt; do not add parsing transformations to the raw layer merely to simplify SQL.

Two execution capabilities are needed; they do not necessarily require separate infrastructure resources:

- **Databricks compute for transformations:** a SQL Warehouse, including a serverless SQL Warehouse, or another compatible Databricks cluster endpoint supported by the adapter executes the SQL generated by dbt.
- **An execution context for dbt Core:** an existing CI runner, orchestrator worker, or Databricks job task with dbt-core and the adapter installed. A scheduler triggers that runtime after ingestion; dbt does not schedule itself. An existing Databricks Job can run the dbt project while an existing SQL Warehouse executes its SQL.

Existing Databricks compute and orchestration can be reused. A new cloud service, storage layer, or dbt Cloud subscription is not inherently required; a suitable CLI runner or SQL endpoint is needed only if none exists. Configure authentication, permissions, environment-specific schemas, and dependency versions.

## 3. What are the upsides and downsides of using dbt-core?

### Upsides

- **Modular SQL and dependency DAG:** separate item, event, and mart models while retaining clear execution order and avoiding one long transformation notebook.
- **Tests:** attach key, relationship, and accepted-value tests to models, plus SQL checks for parameter conflicts and yearly reconciliation.
- **Documentation and lineage:** keep field descriptions and source/model dependencies alongside the transformation code.
- **Incremental models:** reduce repeated processing when data grows, provided keys, late-arrival rules, and affected-year ranking updates are designed correctly. Incremental configuration alone does not guarantee uniqueness.
- **CI-friendly maintenance:** review SQL changes in Git, build and test them in isolated schemas, and reuse established conventions as analytics models expand.

### Downsides

- Adds another runtime, adapter, dependency set, and configuration surface to maintain.
- Its SQL-centric workflow is less natural for low-level file ingestion or custom PySpark parsing; forcing these into dbt would reduce clarity.
- Does not replace ingestion, scheduling, retries, monitoring, or cloud access management.
- For two sources and one mart, migration and operational overhead may exceed the immediate benefit. The current direct PySpark solution is reasonable at this scale.

## 4. Estimate the implementation effort

**Prototype migration to dbt: approximately 1–2 engineer-days.** This covers adapter/project setup, translating the existing clean and mart logic, basic tests and documentation, and reconciliation against the notebook. Ingestion remains unchanged, and full-refresh processing is acceptable.

**Production-ready implementation for this small pipeline: approximately 3–4 engineer-days total**, including migration and basic operational hardening:

| Work area | Approximate effort |
| --- | --- |
| Setup/configuration: adapter, authentication, environments, existing job scheduling and alerts | 0.5 day |
| Staging/clean models: types, event pivot, contracts, agreed ingestion/replay handling | 0.75–1 day |
| Mart: aggregates, ranking/platform rules, affected-year refresh behavior | 0.5 day |
| Tests/documentation: cast checks, conflicts, references, reconciliation, rerun/backfill cases | 0.75–1 day |
| CI/deployment validation: pipeline integration, retries, backfill verification, deployment smoke test | 0.5–1 day |
| **Total** | **3–4 engineer-days** |

These are engineering-effort estimates, not guaranteed calendar delivery dates. They assume an existing Databricks workspace and access, reusable CI/job infrastructure, a stable source structure with agreed delivery semantics, and no major infrastructure or security approval delays. New platform provisioning, complex CDC, or significant source-quality remediation would require a separate estimate.

## Recommended architecture

**S3 ingestion / raw Delta → cleaned transformations → `top_item` mart.**

Keep ingestion and any parsing best handled in PySpark outside dbt. Introduce dbt where SQL transformations, testing, and documentation provide the most value, while existing Databricks jobs coordinate the complete pipeline. For the current take-home scope, the notebook remains an appropriate implementation; dbt becomes more valuable as the model set and team grow.
